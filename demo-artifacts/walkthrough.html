Paid Media Agent, from the front door to the ledger

A local-first agent that reads ad accounts, explains what changed, forecasts budget scenarios, and proposes changes that wait for a person. This guide follows one question and one change through the code, then maps every package and says what to check.

What it is

One Python process with one DuckDB file. A small agent loop calls a model; the model calls tools; tools do every calculation and return figures with verdicts. The CLI, the HTTP API and the Slack adapter all use the same assembly, so there is one agent, not three.

A question's path

Take "Why did Google CPA change last week?" typed into paid-media-agent ask.

flowchart LR
  S[CLI / API / Slack] --> R[AgentRunner]
  R --> L[Agent loop]
  L -->|system prompt + tools| M[(Model)]
  M -->|tool calls| D[ToolDispatcher]
  D --> T[Tools: reads, compute, history, bandit]
  T --> A[(Artifacts)]
  T --> H[(DuckDB history)]
  D -->|results, offloaded if large| L
  M -->|final answer| C{Answer check}
  C -->|figures sourced| S
  C -->|not sourced: one repair| L
  1. A surface takes the message. surfaces/runner.py owns thread access and turns a conversation into an outcome. The CLI, surfaces/api/app.py and surfaces/slack/service.py all call it.
  2. The loop builds one model call. harness/loop.py sends the system prompt (instructions, resolved calendar windows, the accounts and their goals) and a fixed tool list. harness/context.py stubs old results past a token budget, in the view only.
  3. The model calls tools. harness/tools.py checks the tool exists, is not a raw provider mutation, and that arguments match its schema. A read timeout is retried once; a large result is stored as an artifact and replaced by a stub that keeps its verdicts.
  4. Tools compute. A platform read (tools/reads.py) normalises rows into an artifact and into history. explain_change (analytics/drivers.py) splits the change into drivers that add up exactly. Nothing is left for the model to add up; anything else goes through tools/calculate.py.
  5. The answer is checked. grounding.py looks for every figure in the tool results, the account goals, or the user's words. A failing draft is kept, a host note sends it back once, and what remains unsourced is marked unverified.
  6. Everything is recorded. Messages in store/conversations.py; each model call's tokens, cache use and cost in llm_calls via harness/usage.py.

A change's path

Take "Cut the Performance Max budget to 240". No tool can change an ad account directly.

  1. Propose. propose_change (tools/write_tools.py) asks ProposalService in tools/writes.py to read the current value, classify the risk, and store a typed ChangeSet with a digest. Only operations in the reviewed write policy are admitted. A budget recommendation is proposed by its bandit_run_id, so the model never retypes the number.
  2. Pause. The model calls execute_change, which is gated. If it forgets, the runtime pauses the proposal itself (assembly.py _unpaused_proposals). The reviewer sees a summary written from the record (domain/presentation.py), never the model's wording.
  3. Approve. An authorised approver creates a signed, single-use claim bound to the proposal's revision and digest. Editing the proposal makes a new revision and voids earlier approvals.
  4. Execute once, then read back. WriteExecutor checks the write gate and kill switch, makes one attempt, and reads the value back. The receipt says verified, rejected, failed, or unknown; an unknown outcome is never retried blindly.
  5. Log. Proposed, approved and verified land in change_events, which later explains "what changed and when".

Run paid-media-agent demo --with-proposal to watch all five steps as text on synthetic data. Design notes: docs/architecture/writes-and-approvals.md.

The visual demo

make demo opens an animated page for Northwind, a simulated store with four campaigns. A simulation is used because it knows what real data cannot: which anomalies were planted and what each campaign's true spend curve is. The page is mostly diagrams, and its centre is a day-by-day replay of the agent at work.

What is on the page

  • Two jobs, two ideas. One series judged twice: a fixed ±50% rule raises 23 alerts on it, all false, and TabPFN's range raises 1, a real problem. Then two true response curves, with budget moving from the flatter to the steeper until the slopes meet.
  • Feature engineering. For each job: a raw daily row, the engineered row TabPFN is given, and what comes back. The measured effect of the feature choices is quoted from the project's backtests.
  • Eight weeks, replayed. One clock drives the conversions gained over budgets left alone, each campaign's budget, the weekly check on every campaign, and a log of what the agent did.
  • The result and the guardrail. The scores, the approval gate with a real readback receipt, the agent's next steps, and a link to the report it wrote.

How it is built

  1. The store. testing/demo_visual.py runs bandit/evaluate.py run_closed_loop three ways (budgets left alone, the agent, the best possible split), keeps every campaign-day, and runs check_anomalies once per week as the history stood that day.
  2. The story. testing/demo_story.py build_story turns the runs, the weekly checks, the truth and the agent's text into one JSON document embedded in the page.
  3. The page. testing/templates/demo.html.j2, demo.css and demo.js: one self-contained file, vanilla JS and SVG, no network. render(t) draws any moment from the clock alone, so scrubbing and video frames match playback.
  4. The video. testing/demo_video.py (make demo-video): one headless Chrome on its own profile sets the clock frame by frame; ffmpeg joins the frames.
  5. The report. The agent's output for the last fortnight (reports/insights.py, reports/charts.py), with next steps written by the real agent loop (testing/demo_narrative.py) and checked against the figures.
  6. Recording and replay. make demo calls neither TabPFN nor a model, even with keys set. It replays fixtures/data/demo_tabpfn_cache.json (the weekly budgets and TabPFN's 19 recorded answers) and demo_narrative.json, and only if the store rebuilt on the machine matches the recorded one. demo --visual --record-watch asks TabPFN only for answers the recording lacks.

paid-media-agent report --insights adds the range and budget panels to a real account's report from stored history, with the free local model by default.

Reading routes

Thirty minutes

  1. README.md, then make demo and read the page it opens top to bottom.
  2. assembly.py: what the agent is made of.
  3. harness/loop.py, the _run method: the whole loop is about 40 lines.
  4. tools/writes.py, ProposalService.propose and WriteExecutor.execute.
  5. docs/architecture/evals.md, the results sections at the end.

Two hours

  1. Everything above, then instructions.md and workspace/skills/paid-media-analysis/SKILL.md: what the model is told.
  2. harness/tools.py and harness/context.py: dispatch, offloading, the context budget.
  3. tools/reads.py and tools/contracts.py: how a provider payload becomes rows, per platform.
  4. tools/compute.py, tools/summary.py, domain/windows.py: the verdicts.
  5. analytics/drivers.py: the decomposition. bandit/posterior.py and bandit/recommend.py: the budget model.
  6. grounding.py and evals/checks.py: how answers are graded.
  7. tests/contract/test_approval_binding.py and test_answer_check.py: the two safety nets, exercised.

Try it

No model key or ad account is needed for the first block.

uv sync
make demo                                      # opens the report page: ranges, curves, an approval
uv run paid-media-agent demo --with-proposal   # the same flow as text
uv run paid-media-agent doctor                 # what is configured, with no secrets printed
make check                                     # lint, format, types, 525 tests

uv run paid-media-agent simulate --days 180    # campaigns with known response curves
uv run paid-media-agent history --scenario baseline --view daily
uv run paid-media-agent bandit evaluate        # the bandit scored against the truth

With a model key in .env (sample data, no ad account):

uv run paid-media-agent setup                  # the local console
uv run paid-media-agent sync                   # build history from the sample accounts
uv run paid-media-agent ask "Why did Google CPA change last week?"
uv run paid-media-agent ask "What if I raise Non-Brand Search by 20%?"
uv run paid-media-agent allocate               # budget recommendations, nothing applied
uv run paid-media-agent usage                  # tokens, cache hits, cost per call

In Docker: cp .env.example .env, then docker compose up --build -d and curl http://localhost:8080/health.

Evals

Thirty questions on synthetic accounts with goals. Each answer gets deterministic checks (tools called, expected figures, grounded numbers, writes left for approval, no errors) and, if those pass, a judge model scoring correct, grounded, complete and clear.

Known limits

  • Synthetic only. Google, Meta and Reddit live payload shapes and Meta's budget units are implemented from published sources and unverified against real accounts.
  • Sample data is 28 days. A monthly report needs 56, so that job is recorded as skipped on sample data; "same days last month" has nothing to compare with.
  • Late conversions. Conversions that arrive after the 7-day maturity window are not counted, so history runs a few percent low and forecast ranges are slightly narrow.
  • Smaller models omit caveats. Haiku 4.5 sometimes leaves out what the tools state (attribution differences, a month with no data yet). Sonnet 5.5 does not.
  • Prompt caching is used for Anthropic models through OpenRouter only.
  • One process. DuckDB lets a single process hold the state file; do not scale the container past one replica.
